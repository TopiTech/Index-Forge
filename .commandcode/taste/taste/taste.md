# Taste
- Prefers rigorous, evidence-driven production reviews scoped from production entry points, trust boundaries, data flows, persistence, external integrations and deployment to prioritize reachable, material risks including defects/contract violations, security/auth/isolation, validation/integrity, concurrency/retries/idempotency/transactions/recovery, and deployment/operations/accessibility. Confidence: 0.95
- Expects reviews to cover first-party runtime code, schemas, migrations, production configuration/infrastructure and behavior-defining tests while excluding third-party/generated/example/dev-only code unless it directly affects production, and to remain strictly read-only without modifying the repository. Confidence: 0.95
- Requires tracing each candidate from entry point to behavior/failure/state change/side effect, inspecting relevant callers/callees/contracts/guards/constraints/configuration/tests/infrastructure assumptions, establishing expected behavior from repository evidence, and actively trying to disprove the candidate before reporting. Confidence: 0.93
- Wants findings reported only when repository evidence establishes production relevance and reachability, realistic trigger, meaningful impact, supported expected behavior, insufficient mitigation, and traceable root cause; explicitly excludes best-practices/style/dependency-age alone/missing-tests-without-underlying-issue/raw search matches/speculative or sufficiently mitigated concerns. Confidence: 0.95
- Requires exactly one category per finding (Defect/Contract Gap/Missing Protection/Risk) and one severity (Critical/High/Medium/Low) with confidence High/Medium/Low (Low allowed only for potential Critical/High with exactly one decisive unresolved assumption), deduplicated by root cause and ordered by severity, confidence and practical impact using consecutive IDs starting at R1. Confidence: 0.96
- Expects fixed output structure: `## Findings` with per-finding `Location`, `Trace / Call Path`, `Confidence`, `Actual Behavior`, `Expected Behavior`, `Conditions / Trigger`, `Evidence`, `Existing Mitigations Checked`, `Impact`, `Root Cause & Fix Direction`, `Verification Plan`, `Unresolved Assumption`, plus `## Workspace Summary` (Overall Assessment, Coverage Analyzed, Unverified Scope, Residual Risks); or `No reportable defects or material risks were identified...` when none qualify. Normally report only High- or Medium-confidence findings. Confidence: 0.96

## Remediation, Testing & Verification
- Prefers an end-to-end remediation pass after a review: every reported finding is fixed, regression-tested and re-verified, not merely reported. Confidence: 0.9
- Requires each new regression test to be proven to fail without its fix (temporarily reverting the implementation and confirming the test catches the regression, ideally reproducing the production symptom). Confidence: 0.9
- Treats a test that can pass vacuously, or whose fixture has drifted from the type contract, as a defect in its own right, and expects such tests to be corrected rather than left as documentation of a behaviour that never occurred. Confidence: 0.88
- Expects tests that assert on implementation source text (`readFileSync` + `toContain`) to be converted into real behavioural assertions, keeping the same number of assertions and every distinct behaviour covered; a purely structural contract (schema/CI/CSS/worker entry) may stay as a source-text check but must be labelled as a static contract. Confidence: 0.88
- Expects the numbers quoted in a findings/ledger document (test counts, bundle sizes, residual-issue counts) to be re-measured and corrected when they turn out to be stale or underestimated, rather than carried forward. Confidence: 0.85
- When a refactor changes the shape of an implementation, expects existing assertions to be rewritten to assert the underlying intent robustly rather than deleted or loosened. Confidence: 0.85
- Requires the whole check suite to stay green and re-run after each logical unit of work: lint, typecheck of every project (app, worker, tests), unit tests, build, plus a Worker dry-run bundle. Confidence: 0.9
- Expects a final reconciliation pass over the diff: scan for debug leftovers, `describe.only`/`.skip`, `@ts-ignore`/`@ts-nocheck`, newly introduced `any`/unsafe casts, and stray untracked files before declaring the work done. Confidence: 0.88
- Expects an independent review of the agent's own changes before finalizing, and expects the reviewer's findings to be fixed and folded back into the findings list. Confidence: 0.85
- Prefers the review outcome persisted as a canonical findings document in the repository (consecutive IDs, severity, confidence, status, root cause, fix direction, verification plan) including an explicit "discarded as false positives" section, kept reconciled with the actual diff. Confidence: 0.87
- Prefers long multi-phase work to be tracked in an explicit task ledger with statuses rather than implied from the conversation. Confidence: 0.82

## Parallel Delegation & Ledger
- Prefers large reviews and fix rounds to be split across parallel sub-agents, each given an explicit exclusive list of files it owns, so no two agents edit the same file; dependent work is sequenced (contract-defining backend first, then clients, then tests). Confidence: 0.9
- Requires each delegated agent to report its coverage (files read, with line counts) and the reasons for discarded candidates, and expects the orchestrator to verify the agent's claims against the worktree (marker counts, diff inspection) instead of trusting the completion report. Confidence: 0.88
- When a delegated agent stops mid-task (turn limit, environment error), expects the orchestrator to inspect the actual diff, determine which items already landed, and re-delegate the remainder as smaller focused units (reducing parallelism when agents fail for environmental reasons) rather than restarting from scratch. Confidence: 0.85
- When parallel sub-agents appear to be hanging, expects the orchestrator to poll each agent's status to tell a slow-but-progressing agent from a stalled one, and to take the unfinished item over directly or re-issue it as a smaller unit instead of blocking on it. Confidence: 0.85
- Prefers the remediation round to be driven by one ledger that records, per item, the originating finding ID, severity, an explicit decision code (FIX / FIX-PARTIAL / ACCEPTED / DEFER) with the residual risk stated, the root cause and the fix direction, plus the batch's file ownership and the final verification command list. Confidence: 0.87
- Requires prior findings/status documents to be re-verified independently against the current code (CONFIRMED / PARTIAL / REGRESSED / OPEN / CANNOT VERIFY) and treats a claim proven only by a source-text assertion as "fixed (static only)", not fixed. Confidence: 0.88
- When an intentional contract change breaks existing tests, expects the tests to be rewritten to the new contract without weakening the original intent; when a failing test exposes a genuine production bug, expects the production code to be fixed and the test tightened rather than the test relaxed. Confidence: 0.9
- Requires that no test be skipped, deleted or weakened during a fix round: no `.skip`/`.only`, no assertion removed without an equivalent replacement, no `@ts-ignore`/`eslint-disable`, and no newly introduced `any` outside documented test-double boundaries. Confidence: 0.9
- When production code needs a test-only escape hatch (e.g. a password-only admin fallback), expects it to be explicitly switchable and expects a regression test that turns it off, so the real production path is actually exercised rather than only asserted in a comment. Confidence: 0.88

## Code Style
- Prefers a single owner module for shared state (one read-modify-write implementation, one exported key) instead of per-consumer copies; duplicated caches or duplicated literal keys are treated as a defect. Confidence: 0.87
- Prefers runtime validation of every value read from browser storage or an external API over type assertions, with per-field sanitizers that fall back to a documented baseline. Confidence: 0.88
- Prefers identity-preserving state updates (functional updaters that return the previous reference when nothing changed) so a React effect can never re-arm itself; effects should depend on the primitive values they read, not on the objects they replace. Confidence: 0.87
- Prefers request-identity/generation guards (plus AbortController) for every async flow that can be superseded, and expects the guard to be checked on every branch including the error path. Confidence: 0.87
- Prefers shared request/cancellation state to live at module scope when a hook is used by many components, so one consumer's action can cancel another consumer's in-flight request. Confidence: 0.85
- Expects module-scope caches/state that survive between requests (e.g. a failure back-off map) to expose an explicit reset function for tests, because such state otherwise leaks across test cases and makes an unrelated test fail. Confidence: 0.85
- Prefers importing platform/runtime types explicitly instead of relying on ambient global declaration files, so a separate typecheck project can compile the code under test. Confidence: 0.8
- Requires new production code to avoid `any`, `@ts-ignore`/`@ts-nocheck` and `eslint-disable` outright, fixing root causes rather than suppressing symptoms. Confidence: 0.9
- Prefers API and schema changes to stay backward compatible: new fields are additive, legacy rows and missing columns get explicit fallbacks, and the client migrates old persisted formats on read instead of dropping them. Confidence: 0.85
- When adding an expiry, revocation or rotation rule to existing data, expects pre-existing records to be grandfathered rather than locked out: an unknown/undated row is treated as still valid, and the migration or runtime provisioner backfills the timestamp so those rows then enter the normal window. A rule that silently locks out every existing owner is a Critical regression. Confidence: 0.9
- Expects quotas and budgets to be charged for the work actually performed (e.g. only the tickers that must be fetched, not the ones already cached), so a legitimate client is never throttled by no-op requests. Confidence: 0.85
- Expects the client to handle server-side credential expiry: on a rejection that means the session/token is dead, drop the stale credential and prompt for re-authentication instead of showing a generic error. Confidence: 0.85
- Expects comments to explain non-obvious invariants and the reason behind a decision, not to narrate the diff. Confidence: 0.85
- Prefers bundle-splitting/performance claims to be verified against the built artifact (e.g. the first-paint chunk list in the built HTML) rather than against the source, and gates regressions with size budgets instead of hashed chunk names. Confidence: 0.82
- Uses Japanese for user-facing strings and domain comments and English for structural/API comments in this codebase. Confidence: 0.8
